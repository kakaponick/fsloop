# fsloop

Скилл Claude Code: задача любого размера (фикс, фича, страница, сервис, воркер, крон, миграция) от промпта до коммита без надзора. Каждая единица работы — вертикальный срез через все слои, UI и бэкенд вместе. fsloop строит карту кода и неизвестных, проверяет неизвестное на живой системе (спайки), режет работу на юниты и ведёт каждый red → green в отдельном worktree, отлаживает, ревьюит (код, рантайм, UI через impeccable), коммитит по юниту, интегрирует и проверяет деплой. С `N` после этого оценивает результат и дорабатывает, пока не сойдётся.

| `skills/fsloop-audit/` | `/fsloop-audit`: аудит fsloop по записям его прогонов — куда уходит время, какие находки теряет фильтр критиков, какие баги не поднял ни один критик, соблюдают ли прогоны скилл; отчёт, файл находок для `/fsloop` и предложения для `/evolve` |

## Требования

- Claude Code, который подставляет `${CLAUDE_SKILL_DIR}` в текст скилла (проверено на 2.1.319): из неё оркестратор пишет строку `Skill:` в `common.md`, и по ней скилл и агенты находят `fsl.mjs`, `law/` и остальные файлы — в файлах fsloop эта папка записана как `<skill>`.

- git, Node 24+ (хук `spike-guard` опирается на `import.meta.main`).
- Плагин `mattpocock-skills`: агенты грузят `tdd`, `diagnosing-bugs`, `codebase-design`, `code-review`.
  ```
  /plugin marketplace add mattpocock/skills
  /plugin install mattpocock-skills@mattpocock
  ```
- Для UI-юнитов — скилл [impeccable](https://github.com/pbakaus/impeccable) в `.claude/skills/` проекта или в `~/.claude/skills/`. Если в проекте есть `components.json` (shadcn/ui), пригодится и скилл `shadcn`.
- Необязательно:
  - скилл `ai-socket` — вопросы разработчику через Telegram (код входа, деньги, аккаунт). Без него такой шаг уходит в OPEN.
  - скилл `prod` (или раздел в `CLAUDE.md`) с командами чтения продакшена — для формы данных на Map и для `prod-check` после пуша. Без него форма берётся из схемы, проверки деплоя нет.
- Windows: `spike-lease` делает junction (`mklink /J`) и hardlink, прав администратора не нужно.

## Установка

fsloop ставится один раз на машину, а не в каждый проект: `~/.claude` ссылается на этот клон, и правка в нём сразу видна во всех проектах.

```
git clone https://github.com/kakaponick/fsloop
node fsloop/install.mjs                  # машина
node fsloop/install.mjs <путь к репо>    # машина и проект
```

Установщик:
- ставит четыре ссылки — `~/.claude/skills/fsloop` → `skills/fsloop`, `~/.claude/skills/fsloop-audit` → `skills/fsloop-audit`, `~/.claude/agents/fsloop` → `agents`, `~/.claude/hooks/fsloop` → `hooks`. Это junction: файловый симлинк Windows делает только в режиме разработчика, junction — всегда; агентов из папки внутри `agents/` Claude Code читает так же, как лежащих в ней;
- добавляет хук `spike-guard` в `~/.claude/settings.json`;
- ссылку, которая ведёт в другое место, переставляет на этот клон; настоящую папку или файл на месте ссылки не трогает и останавливается;
- с путём к репо — переносит старый `.spike/` в `.claude/fsloop/spike/` целиком (не трогает его, пока у сессии есть аренда или worktree держит его зеркало), добавляет `.claude/fsloop/spike/` в `.gitignore`, а в `.git/info/exclude` — `.claude/fsloop/*` и `!.claude/fsloop/config.md` (папки прогонов не попадают в git, `config.md` попадает), создаёт `.claude/fsloop/spike/{data,sessions,toolkits}` и шаблон `README.md`, и называет копию fsloop, которая осталась в проекте (`.claude/skills/fsloop`, `.claude/skills/fsloop-audit`, агенты, хук в `.claude/settings.json`), — её надо удалить, чтобы работала только глобальная, — `CLAUDE.md` или файл `.claude/rules/`, где ещё написано `.spike/`, и `config.md`, где команды съёмки ещё идут через `<start>/.claude/skills/fsloop/` вместо `<skill>/`.

`.claude/fsloop/spike/` попадает в `.gitignore`, хотя `.git/info/exclude` и так прячет всё под `.claude/fsloop/`, кроме `config.md`: exclude живёт только в этом клоне, а сессии и токены не должны попасть в коммит и из свежего клона.

`--claude-dir <папка>` ставит ссылки и хук в другую папку вместо `~/.claude`. Повторный запуск ничего не дублирует.

## Проект

fsloop берёт всё про проект из его `CLAUDE.md` (и файлов правил, которые тот называет) и из манифеста пакетов: установку, проверку типов, линт, тесты (один файл и весь набор), гарды каталогов, сборку, генерацию и применение миграций, запуск воркера, основную ветку, машинный лок, инструменты скриншотов, строгие правила. Всё это он записывает в `common.md` прогона, и агенты читают только его. Чего в проекте нет — решение, оно попадает в отчёт. Чем подробнее `CLAUDE.md`, тем меньше догадок.

**Конфиг `.claude/fsloop/config.md`** (необязательный, коммитится) закрепляет всё это явно, и прогон берёт его как есть, ничего не выводя заново: заполненную таблицу ролей-команд из SKILL.md → Project facts, карту ролей UI (`law/ui.md` → Roles: какой компонент — статус-точка, тултип-глоссарий, адаптивный тулбар, таблица…) и то, чего документация проекта не говорит, а прогон должен знать. С ним поведение fsloop в проекте одинаково от прогона к прогону.

**Закон.** fsloop несёт свою планку: `law/` — UX, UI, код, тесты. Она действует в любом репо; правила проекта (`CLAUDE.md` и файлы, которые он называет) уточняют или переопределяют её там, где говорят о том же. Ссылки в находках — по номеру: `ux 1`, `table #10`, `tests 6`, `code` → Idempotent. Правило с пометкой *default* — выбор для плотного рабочего инструмента; `PRODUCT.md` или `DESIGN.md` другого продукта может его заменить.

Кадры UI снимает только оркестратор и только дважды: baseline на Map и final на Review. Агенты не открывают ни браузер, ни dev-сервер (исключение — `fsloop-shots` на init): состояния доказывают тестами, а кадр читают по пути.

Для UI fsloop читает `PRODUCT.md` и `DESIGN.md` (это файлы impeccable), закон fsloop `law/ui.md` и `law/ux.md`, а поверх — правила UI/UX проекта, если `CLAUDE.md` их называет. Кадры снимаются по рецепту из `config.md` → Shots, который проверил `/fsloop init`. Без него — инструментом скриншотов проекта, если `CLAUDE.md` его называет, иначе `shot.mjs`.

i18n-каталоги, которые сливаются по ключам, перечислены в `skills/fsloop/merge.attributes` (`messages/*.json`, `locales/**/*.json` …). Если у вас другой путь — допишите его туда.

## Spike lease (опционально)

Нужен, только когда агенты работают с живыми аккаунтами — сессиями, которые нельзя поднимать из двух процессов сразу (мессенджеры, кабинеты с привязкой к IP). Если аккаунтов нет, `.claude/fsloop/spike/sessions/` пуст, `link` даёт пустое зеркало, `acquire` не вызывается — настраивать ничего не нужно.

Как работает:

- Аккаунт — папка `.claude/fsloop/spike/sessions/<name>/` в основной рабочей копии.
- Каждый worktree прогона получает зеркало `.claude/fsloop/spike/` ссылками — всё, кроме `sessions/`.
- `acquire` берёт атомарную аренду (`.lease` в папке сессии) и только тогда ссылает папку в worktree. Без аренды папки в worktree нет: скрипт или тест падает на отсутствующем пути, а не делит сессию с другим процессом.
- `spike-guard` блокирует обход: ручные ссылки в `.claude/fsloop/spike`, копирование из `sessions/`, удаление `.lease`. Старый `.spike/` он охраняет так же, пока проект не перенесён.

```
node ~/.claude/skills/fsloop/spike-lease.mjs link <checkout>
node ~/.claude/skills/fsloop/spike-lease.mjs acquire <checkout> <session> [--wait s]
node ~/.claude/skills/fsloop/spike-lease.mjs release <checkout> <session>
node ~/.claude/skills/fsloop/spike-lease.mjs unlink <checkout>
node ~/.claude/skills/fsloop/spike-lease.mjs status
```

Пробы в worktree не кладите под `.claude/fsloop/spike/`: это ссылка в основную копию, файл окажется там, а импорты разрешатся от её конфигурации, а не от worktree.

## Запуск

```
/fsloop <goal>              один проход: карта → юниты → ревью → фикс → интеграция
/fsloop 3 <goal>            до 3 проходов с оценкой и доработкой
/fsloop 3 j1 <goal>         последовательно, одна полоса
/fsloop resume <run id>
/fsloop spike <question>    только исследование, без коммита
/fsloop init                заполнить и проверить .claude/fsloop/config.md
```

Маленькая цель (меньше 3 юнитов) идёт в режиме inline прямо в текущей рабочей копии. Остальные — в worktree `../fsl/<run id>`, с полосами `../fsl/<run id>-u<k>` для параллельных юнитов. Состояние прогона лежит в `.claude/fsloop/runs/<run id>/`.

Коммиты прогона несут трейлеры `Fsloop-Run`, `Fsloop-Step`, `Fsloop-Pass` и `Fsloop-Closes` (какие находки закрывает коммит), поэтому `git log --grep='Fsloop-Run: <id>'` показывает весь прогон. В конце fsloop пушит в основную ветку. Если `CLAUDE.md` запрещает агенту такой пуш, ветка `fsl/<run id>` уходит в origin, и отчёт называет её для слияния.

## Папка прогона

Всё, что прогон сделал и решил, лежит в `.claude/fsloop/runs/<run id>/` по одной раскладке (SKILL.md → Run folder). Её читает и интерфейс.

```
common.md              памятка агентам; в начале Run/Mode/N/K/Start/Worktree/Started, Session на каждую сессию, ## Goal
journal.md             решения оркестратора: | # | stage | question | decision | why | refs |
units.md               состояние задач: | unit | pass | state | tree | title |
units/<u1|f1>/         brief.md, commit.txt, tests.log, логи проверки и слияния
launches.md            каждый запуск агента: кто, модель, agent id, время, токены (свои и его под-агентов), транскрипт, отчёт
reports/<launch>.md    итоговый блок каждого запуска, дословно
findings/<stage>.md    решение по каждой находке: | finding | decision | ref | repeat | why |
decisions.jsonl        каждое изменение строки в findings/ — история решений
passes.md              с N: | pass | taken | outcome | why |
surfaces/, shots/, logs/
gates.jsonl            итоги проверок шагов, все попытки
run.json, summary.json весь прогон одним документом; короткая строка для списка прогонов
human.jsonl            пишет интерфейс: оценка пользователя находке, запуску или решению
report.md
```

Прогон — это цепочка шагов `p<проход>-<шаг>`: `map`, `spike`, `decompose`, `units`, `review`, `fix`, затем `verdict` (без N) или `assess` (с N), потом `integrate` и `finish`. Шаг считается завершённым, только когда `fsl.mjs gate` его пропустил, и следующий начинается только после этого. Проверка красная, если:

- отчёт запуска не сохранён;
- у находки нет строки с решением, у решения нет причины, или у `dropped`, `declined`, `duplicate` нет ссылки. Ссылка — `j<n>` (строка журнала), id находки или `law:<файл> <правило>`;
- строку под FINDINGS или VERDICT не удалось разобрать (`<запуск>#line-<k>`), и ни одна строка журнала её не называет;
- в журнале два ряда с одним `#`;
- у собственной находки прогона (`<stage>-own#<n>`) нет колонки `severity` или `evidence` (строка лога, которая её показывает);
- находка «в работу» не названа в `## Closes` ни одного брифа;
- в брифе нет одного из разделов, или в `## Files` нет ни одной строки ``- `<путь>` ``;
- два брифа пишут один файл (кроме общих каталогов из `merge.attributes`), и нет строки журнала, которая называет оба и объясняет, почему их нельзя слить в одну задачу;
- коммит задачи без трейлеров, или пустая строка внутри трейлеров прячет их от `%(trailers)`;
- на вопрос исполнителя «на суд» (`to judge:`) нет ответа критика с его id и нет строки журнала, что он оставлен открытым;
- с N число `taken` в `passes.md` не совпадает с находками, отданными следующему проходу, или итог прохода не следует правилу;
- с N после первого прохода осталась находка, которую не отдали второму проходу и не закрыли иначе, или не запущен поиск улучшений там, где он положен;
- перед пушем (`integrate`) осталась открытой critical или major находка ревью, вердикта, последней проверки слияния или собственная находка прогона (красная проверка, которую не смогли починить). Пуш тогда не делается, а прогон всё равно завершается отчётом;
- в `report.md` нет таблиц, которые пишет `fsl.mjs report`.

```
node ~/.claude/skills/fsloop/fsl.mjs save   <run folder> <stage> <agent id | output_file | "описание запуска"> ["описание"]
node ~/.claude/skills/fsloop/fsl.mjs gate   <run folder> <stage>
node ~/.claude/skills/fsloop/fsl.mjs report <run folder>
node ~/.claude/skills/fsloop/fsl.mjs build  <run folder>
```

Id находки — `<запуск>#<id>` (`p1-review-critic-code#code-3`). Повтор того же id в одном отчёте получает номер по порядку (`code-3~2`), строка OPEN исполнителя или отладчика — `<запуск>#open-<n>`. Каждая строка отчёта сохраняется: `parsed: "strict"`, если она по формату критика, `"loose"`, если поля восстановлены (тогда рядом и исходная строка `raw`).

Статус находки (`status`) `run.json` вычисляет так:
- `undecided` — нет строки решения; `candidate`, `dropped`, `declined`, `duplicate`, `open` — решение как есть;
- `queued` — взята в работу, задачи ещё нет (в Integrate — после неё не было запуска `integrate fix`); `in-progress` — задача идёт; `blocked` — задача заблокирована;
- `fixed` — исправление в коммите. `closedBy` говорит, что его видело потом: `not-reraised` — критик, смотревший результат позже (ревью экрана задачи или оценка с N), её больше не поднял; `integrate-recheck` — критик слияния прошёл после исправления; `null` — пока ничего;
- `closed` — только вердикт `resolved` (`closedBy: verdict`); `unresolved` — вердикт `partial` или `unresolved`;
- `repeated` — более поздняя находка назвала её в `repeat`: исправление не удержалось.

`effectiveStatus` — судьба по цепочке: у дубликата — того, что он повторяет, у повторённой — того, что её повторило, до конца цепочки; `supersededBy` называет этот конец. Обратные ссылки: `duplicates[]`, `repeatedBy`.

В `run.json` (`version` меняется с каждой сменой формы, `generator.fsl` — хеш `fsl.mjs`) также:
- `now` — где прогон сейчас: шаг, с какого времени, чего ждёт (запуски в работе, незавершённые задачи, последняя красная проверка); `running[]` — запуски текущей сессии оркестратора, ещё не сохранённые;
- `outcome` — запушено ли (`pushLine`), удержанные находки, вердикт `prod check`, достигнута ли цель;
- у каждого запуска: блок отчёта по разделам (`block`), задача, `agentId`, начало и конец, токены свои и под-агентов (`spend.children`), `transcriptGone`, если Claude Code уже удалил транскрипт (отчёт остаётся); у оркестратора — токены его сессий;
- `commits[]` — коммиты прогона из git по трейлерам (после rebase — актуальные sha), у задач и находок — свои; `null`, если git недоступен;
- у находки: прежние версии её строки решения (`history`; весь журнал — `decisions.jsonl`) и когда принята нынешняя (`decidedAt`), куда ведёт ссылка (`refKind`, `refJournal`), строки журнала о ней, коммиты, вердикт, оценка пользователя (`human`). Ключ находки, у которого значение `null`, `false` или пустой список, не пишется: находок в большом прогоне тысячи;
- вердикты (`verdicts[]`, `matched` — какую находку закрывают), вопросы «на суд» (`<запуск>#judge-<n>`) с ответом критика и названной им находкой;
- проверки каждой задачи и лога (`checks`, `logs[]` из `*.lines`), кадры `shots[]`;
- оценки каждого экрана по проходам: `p1-map` (до изменений) → ревью → `p1-assess` → `p2-assess`, audit и critique.

Интерфейс показывает прогон только из рабочей копии, которую называет `Start:` в его `common.md`: полосы держат копию `common.md` и брифов в своей `.claude/fsloop/runs/<id>/`, но не `run.json` (`mirror: true`, если `build` всё же запустили там). Папки старых версий `.claude/fsloop/<id>/` — только отчёт: `build` пишет для них `run.json` с `legacy: true`. Для списка прогонов хватает `summary.json`. Несогласие пользователя интерфейс дописывает в `human.jsonl`; следующий прогон превращает каждую такую строку в предложение в `.claude/evolve/inbox/`.

`fsl.mjs report` вписывает в `report.md` таблицы из папки прогона: решения, задачи, находки со статусом, вопросы «на суд», кандидаты, проходы и оценки экранов. Таблицы перегенерируются на месте, руками их не правят.

## Init

`/fsloop init` — один раз на проект и после смены стека. Агент сам заполняет `.claude/fsloop/config.md` и проверяет каждую строку настоящим запуском.

Конфиг короткий: его читает каждый прогон и целиком получает каждый агент. В нём только то, по чему прогон действует (команда, путь, правило). Доказательства — коды выхода, секунды, логи, кадры — остаются в папке прогона init. Где сказать нечего, стоит `none — <почему>`.

- **команды** — каждая роль (установка, типы, линт, тесты, гарды, сборка, миграции, воркер…) запускается один раз в отдельном worktree, лог остаётся в папке init. Все команды идут на одноразовой базе `<base>_init_<run id>`: init создаёт её, накатывает миграции и в конце удаляет. Красное на main — это факт, а не повод менять команду: в конфиге пара слов после команды, например «red on main: 3 errors»;
- **каталоги и гарды** — какие общие файлы пишут несколько задач и какой тест краснеет, когда они растут;
- **карта ролей** — какой компонент проекта играет каждую роль из `law/ui.md`;
- **дизайн** — единственный шаг, где init спрашивает пользователя; impeccable работает в worktree init, и его файлы коммитятся вместе с конфигом. Если `PRODUCT.md` нет или он устарел, запускается `/impeccable init` (интервью о продукте). Дальше одно из трёх: `DESIGN.md` есть — конфиг ссылается на него; дизайн-система есть в коде — `/impeccable document` фиксирует её в `DESIGN.md`; иначе пользователь выбирает, задать визуальное направление сейчас или позже. Сейчас — `/impeccable document --seed`: пользователь выбирает направление, impeccable пишет черновой `DESIGN.md`, экран не строится. Позже — конфиг пишет `direction: later`, и первый прогон с UI сохраняет текущий вид;
- **съёмка** — агент `fsloop-shots` подбирает способ (свой инструмент проекта или `shot.mjs`), проверяет подъём данных, сервер, вход, кадр и остановку и снимает три кадра: страницу без входа, страницу за входом с данными, диалог. Отдельный агент смотрит на кадры и подтверждает, что на них то, что нужно, а не форма входа, ошибка или пустая страница. Нет тестового пользователя — рецепт сохраняется без входа, и хватает двух кадров.

Чего в проекте нет (сида, тестового пользователя, сухого режима воркера), init не пишет сам — он называет это в итоге, вместе с тем, куда попал конфиг: в основную ветку, в ветку для слияния или никуда (worktree остаётся). Гейт `fsl.mjs gate <папка> init` не пропустит конфиг, если: у роли нет строки; у запускаемой роли нет лога запуска; нет раздела про каталоги, роли или дизайн (или `- none — <почему>`); кадры не подтверждены как «ok» — три, или два, когда в рецепте `login: —`.

`shot.mjs` работает через `puppeteer-core` и установленный Chrome. Если `puppeteer-core` нет в проекте, он ставится один раз вне репо: `npm i --prefix ~/.fsloop puppeteer-core`; Chrome ищется в системе или по `CHROME_PATH`. Сессия входа хранится в `.claude/fsloop/auth.json` (не в git), пароли — только в переменных окружения или `.claude/fsloop/spike/`. Сервер для съёмки работает на своей одноразовой базе `<base>_shots_<run id>`, а все переменные внешних сервисов (ключи, токены, адреса очередей, кешей, почты, хранилищ) пустые; файлы env никто не читает целиком, только имена переменных. `shot.mjs stop` останавливает только процесс, который запустил `serve`: рядом с pid записано время его старта, и чужой процесс с тем же pid не трогается.

## fsloopUI

Интерфейс прогонов fsloop: слева карточки прогонов всех проектов (проект, настройки, состояние), справа открытый прогон — его находки, юниты, отчёты критиков, соглашения и журнал решений. Данные обновляются вживую, без перезагрузки. Папку прогона разбирает сам `fsl.mjs` (`collect` и `build`), поэтому интерфейс и скилл видят одни и те же находки, решения и статусы. Закрытый прогон читается из его `run.json`.

Сервер слушает только `127.0.0.1` и ничего не меняет в папках прогонов. Единственное, что он пишет, — оценку пользователя в `human.jsonl` прогона. Node 24 запускает TypeScript сервера как есть, без сборки.

```
cd fsloopui
npm ci
npm run build
npm start -- <корень проектов> --port=4747
```

`<корень проектов>` — папка, в которой лежат проекты (например `~/Desktop/dev`), сам проект или папка одного прогона. Можно передать несколько корней; без корня берётся текущая папка. Интерфейс открывается на http://127.0.0.1:4747/.

`npm run fixtures` пишет в `fixtures/root/` тестовый корень: 5 проектов и 63 прогона, среди них один прогон размера самого большого настоящего (723 находки). Времена файлов отсчитываются от текущего момента, `--now=<ISO>` задаёт его явно.
