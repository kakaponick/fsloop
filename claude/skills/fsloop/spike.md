# fsloop — Spike

A **spike** is a time-boxed investigation that ends in facts, not product code: a doc a developer builds on and a toolkit the next spike starts from. The `spike-researcher` agent (`.claude/agents/`) does the work; you frame, launch and verify. Two entries: step 2 of a run, for every unknown Map left without a doc; and `/fsloop spike <question>` — a research-only run with no worktree, no lanes and no commit, in the checkout it was started in, since a spike writes only under `docs/` and `.spike/`.

1. **Frame.** The question in the user's words (in a run: the unknown's line from Map). The deliverable: what will be built on the answer, hence what the doc must settle — transport, auth, envelopes, objects, limits, risks; or a format's layout; or a behaviour's exact rule. Prior art: the repo's findings docs and toolkits (`docs/api/*.md`, `docs/research/*.md`, `docs/*.md`, `.spike/toolkits/*/README.md`) — a doc that already answers part of it is named so the spike extends instead of repeating; the best of them is the **reference doc** whose shape the new one matches. Topic slug → the doc at `docs/api/<topic>.md` (an API) or `docs/research/<topic>.md` (anything else), the toolkit at `.spike/toolkits/<topic>/`.
2. **Resources.** `.spike/` in the repo root (gitignored) is the research workspace: `README.md` in the user's words at the root; shared data — proxies, samples, exports — in `.spike/data/`, what each thing is and any limits; each account in `.spike/sessions/<name>/` (anything that opens the account: session string, tdata, cookies, 2FA); under `.spike/toolkits/<topic>/` each investigation's own toolkit and probes. Read the README; missing → say what to drop there and continue with the offline branches (the system's own code, docs). Accounts and their state — lease, last health, proxy, flags — come from the project's account tool when `CLAUDE.md` names one, else from `spike-lease.mjs status` and the README; the launch names accounts as that source does. The README's limits are the only limits; none written → none. A probe that needs production-like conditions — a deployed copy, a real container, Linux — runs where the project's rules allow a scratch deployment (a staging host, `spike-*` resources beside production), never inside the production stack; none named → the step is OPEN. A fixture the probe needs and `.spike/` lacks: not critical (a sample record, a stub reply, a test name, email or city that reaches nothing the user answers for) → generated, marked synthetic in the toolkit README and the doc; critical (money — a funded account, a paid call — or an account `.spike/` lacks) → the researcher's own `socket ask` (skill `ai-socket`, when installed), and the step waits; silence or no `ai-socket` → the step stays open, never a guess.
3. **Lease.** An account is used by one process at a time — two clients on one session lose the auth key. Before the launch, `node <start>/.claude/skills/fsloop/spike-lease.mjs acquire <checkout> <session>` for every session the question needs (busy → `--wait <s>`, or report who holds it); `release` after the report. In a plain checkout this only marks the lease; in a worktree it also links the folder in (`backend.md` → Sessions). In a run the checkout is `<wt>`; no two spikes of one message share a session.
4. **Launch** `spike-researcher` (foreground, `model: opus`) with: `Repo:`, the question, the deliverable, prior art, the doc path and toolkit dir, the reference doc and toolkit or `none`, what `.spike/` holds and which sessions are leased. Several independent unknowns → one launch each, in one message, at most `K` in a run.
5. **Verify the report.** Every ANSWERED line carries evidence (`live <date> <script>` or `source <file:line|url>`); a claim without one moves to UNVERIFIED before it reaches a brief or the summary. The doc exists at the path, the toolkit's README lists the gotchas hit. In a run: ANSWERED lines become facts a brief may cite; UNVERIFIED lines become done-criteria where `.spike/` makes them verifiable, otherwise the unit builds on the doc and the report marks it `unverified live`; OPEN lines naming a missing resource → decisions, with what to drop into `.spike/`. In a worktree run the docs are committed on `fsl/<run id>` as a command list before any lane opens (SKILL.md → step 2), so every lane sees them; in an inline run the checkout is the start checkout and the doc commits with the work; after a research-only run the doc is the user's to commit. The toolkit stays in `.spike/`.
6. **Notify.** `socket notify --topic spike/<topic> "<RESULT line + OPEN items>"` (skill `ai-socket`; not installed → skipped) — the developer may have left the terminal while the researcher waited on them. In a run the notification is the journal line; the report carries the spikes table.
7. **Summary** of a research-only run, in the user's language: answered (claim → evidence) · unverified and why · risks (rate limits, anti-bot, owner notifications, geo) · what to add to `.spike/` for the next run · files.
