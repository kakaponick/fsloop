# fsloop — the assessed loop

Read at bootstrap when `/fsloop` got `N`; without `N` nothing here runs. After Fix it adds an assessment that decides whether another pass is built; the baseline every run takes at Map (`ui.md` → Baseline) is where each surface's audit scores start.

## Passes

A **pass** is steps 3–6 of SKILL.md, then Assess. The first pass builds the goal; each later pass builds only the gap Assess found — its findings decided `fix`, ref `p<p+1>`, each under a brief's `## Closes` — and starts at step 3, or at step 1 when it needs Map — only for a surface no earlier pass mapped (its production shape and baseline) — or Spike — only for an unknown the findings name that no doc covers. Weight earns a pass: critical and major findings above the bar open the next one; minors go to candidates — a pass costs five launches, a unit and, per surface, the craft launches of `ui.md`'s table; a minor does not pay for it. The run ends when it **converges** (an assessment with no critical or major above the bar), **stalls** (their count, declined excluded, did not fall against the previous assessment — or every one of them sits on code the previous pass wrote: fixes of fixes are a stall, decided `open`), or after pass `N`. The audit score per surface and any reversal are reported, never stop conditions.

## Craft assessment

The design instrument for a surface the goal makes or reshapes, at each Assess: the baseline's launch (`ui.md` → Baseline) on the surface as the pass left it, the pass's final frame by path and the fix patches since, description `craft <surface>`. Its `AUDIT:` scores and its critical and major findings are the surface's count, the same assessment at every stage, so baseline → now compares; a new surface's count starts at its first `AUDIT:` score.

**A surface barely changed since its last score** takes no launch and keeps that `AUDIT:` score, Review's included: fewer than 10 lines added plus deleted in its primary component file or route directory, test files excluded, since the commit that score judged — for Review's, the parent of its pass's first `Fsloop-Step: f<k>` commit; for an Assess's, that pass's last commit (`git -C <wt> diff --numstat <commit> HEAD -- <path> ':!*.test.*'`) — and no finding decided `fix` from that score's report on: neither a critical or major one on it, nor a `component` one on a file it imports (`git -C <wt> grep -l` of its import), nor any `token` one. A journal row names the surface, the line count and the score it keeps. A surface with no score yet takes its launch.

## Assess

After Fix, every lane closed. A craft assessment of each surface the goal makes or reshapes, unless it barely changed since its last score (Craft assessment). `fsloop-critic` in assessment mode — `LENS: code assess` always (description `critic code`), `LENS: runtime assess` when the run has a backend part (`critic runtime`) — on everything the goal touched: briefed with the goal in the user's words, the spike docs, the production shape of every surface and the full file list of the run; no unit brief, no settled decisions, no prior findings: the built result is judged as a stranger would judge it. The **end-to-end run** — the goal's scenario run for real per The end-to-end run below (a page's task walk is its implementer's tests, not part of this run). Last and alone — every launch done, every shot server stopped — one background command list (SKILL.md → Background commands), its log `logs/p<p>-assess-suite.log`, with the suite and the whole-repo lint on the run branch, the pass's only whole-suite run; its red lines judged by step 7's suite rules (a red line major, its flaky and time exceptions), each the run's own finding `p<p>-assess-own#<n>` (SKILL.md → Findings), decided here like every other. Judge every finding by the bar in `findings/p<p>-assess.md`, with two differences: a settled decision the assessment overturns is reopened, never dropped; a finding on what no pass of this run built is a candidate. A finding that shows an earlier `fix` finding still standing names it under `repeat` — that fix did not hold. Then decide by the rule of Passes, a row in `passes.md` — the pass, its critical+major above the bar (`fix` or `open`, declined excluded), the outcome and why: converged · stalled · next (back to step 3, the findings decided `fix` with ref `p<p+1>` as the goal) · cap; when the run stops here, its critical and major are `open`. Done when `gate p<p>-assess` is green: it recounts critical+major from the findings and refuses an outcome the rule does not allow.

**Handoff.** A `next` hands the run to a fresh session: yours holds every brief and report of the pass, and turns are the price, while the run folder holds all the next pass needs (SKILL.md → Resume). Once `gate p<p>-assess` is green, no launch running, no lane open and every background command and Monitor of yours stopped (`TaskStop`): first the journal row `handoff`, then load T3 Code's thread launcher (`ToolSearch` `select:mcp__t3-code__t3_thread_launch`) and launch one thread — `clientRequestId` `fsloop-<run id>-p<p+1>`, the same on a retry; no `projectId`, model or modes (inherited); `workspaceStrategy` `{type: "existing_worktree", worktreePath: <start>}` when `<start>` is not the project's root checkout, none when it is; title `fsloop <run id> · pass <p+1>`; message `/fsloop resume <run id>`, then the user's in-run instructions verbatim, each with its journal row. End your turn with one line and the thread's link. No launcher in reach → the next pass runs in this session, a decision.

Finish's report carries the passes and each surface's audit and critique scores, baseline → now (`fsl.mjs report`), and, in the summary, converged, stalled or cap, at which pass, with the count that decided it, and the audit and critique scores per surface, baseline → now.

## The end-to-end run

The goal's scenario runs for real in `<wt>`: a job enqueued through the service and taken by the worker command (`common.md`) in its dry mode when it has one, against a throwaway database of the run (`<db>_e2e_<run id>` created beside the dev database, the migrate command applied into it, dropped at Finish) — never the shared dev database, whose accounts and jobs another process may hold, and never a live transport from the worker while a live session may be held elsewhere (`backend.md` → Sessions); the row's transitions read back by SQL; a cron's `run` called directly; a client method against the live system where `.spike/` allows — that step goes to a `spike-researcher` with the toolkit and the law's path, sessions acquired for `<wt>` for the run's duration and released after (no lane is open at Assess). A project with no worker or no database runs the scenario through its own entry point (a CLI, a request to the dev server), the same evidence rule. Each command list's COMMANDS lines become the evidence table (criterion / command / outcome); a step nothing in `.spike/` covers is a decision and `unverified live` in the report. Money — a payment, a paid call, a budget top-up — is never spent by the run: such a step is `unverified live` with the reason, and the report names it for the user.
